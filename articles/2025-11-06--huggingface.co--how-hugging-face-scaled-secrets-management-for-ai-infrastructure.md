## 概要 (TL;DR)

Hugging Faceは、AIインフラの急成長とマルチクラウド環境への移行に伴う秘密情報管理の課題を解決するため、Infisicalを導入しました。これにより、秘密情報の散乱、複雑な権限管理、ローカル開発の非効率性といった問題を解消し、セキュリティ体制を大幅に強化するとともに、エンジニアの生産性を向上させました。Infisicalは、Kubernetesとの連携、きめ細やかなアクセス制御、CI/CDパイプラインへの統合を通じて、開発から本番環境まで一貫した安全な秘密情報管理を実現しています。

## 重要ポイント

*   **秘密情報管理の一元化と標準化**: AWSからAzure、GCPを含むマルチクラウド環境全体で秘密情報管理をInfisicalに集約し、一貫性を確保。
*   **Kubernetesとのシームレスな統合**: Infisical Kubernetes Operatorにより、秘密情報の自動同期と更新が可能になり、セキュリティと運用効率が向上。
*   **セキュリティ体制の強化**: Oktaとの連携によるきめ細やかなロールベースアクセス制御（RBAC）と、自動監査、安全な秘密情報ローテーションを確立。
*   **開発者体験の向上**: Infisical CLIにより、ローカル開発環境での安全な秘密情報注入を実現し、`.env`ファイルの利用を排除。
*   **CI/CDパイプラインへの統合**: GitHub Actions、OIDC認証、Terraformを通じてデプロイパイプラインに組み込み、エンドツーエンドのセキュリティを確保。
*   **エンジニアリング時間の節約**: 手動での秘密情報設定が不要になり、オンボーディングと開発サイクルが加速。

## 詳細レポート

### What happened
Hugging Faceは、AIインフラの急速な拡大とマルチクラウド化に伴い、秘密情報（シークレット）の管理に課題を抱えていました。既存のシステムを再構築したり、HashiCorp Vaultのような大規模なソリューションを採用する代わりに、開発者フレンドリーなワークフロー、マルチクラウド抽象化、堅牢なセキュリティ機能を備えたInfisicalを選択し、秘密情報管理システムをInfisicalへ移行しました。

### 背景
Hugging Faceのインフラは、AWS単一からAzureやGCPを含むマルチクラウド環境へと進化し、400万人以上のビルダーがプラットフォームを利用するまでに成長しました。この成長に伴い、以下の主要な課題に直面していました。
*   **秘密情報の散乱（Secret Sprawl）**: 環境間での管理の一貫性の欠如によるリスク増大。
*   **複雑な権限管理**: チーム規模の拡大に伴い、SSO（Okta）と統合された厳格なロールベースアクセス制御（RBAC）が必要。
*   **ローカル開発の課題**: 従来の`.env`ファイルがセキュリティと開発者生産性の両方を損なう。
*   **手動ローテーションの負担**: 過去のセキュリティインシデントで資格情報が露出した経験から、手動での秘密情報ローテーションの負担が顕著に。
また、Infrastructure-as-Codeの実践、プロジェクトごとの秘密情報管理、デプロイ時の自動化と手動制御のバランスも求められていました。

### 影響
Infisicalの導入により、Hugging Faceは以下の影響を受けました。
*   **Kubernetes統合**: Infisical Kubernetes OperatorがInfisicalの秘密情報の変更を継続的に監視し、対応するKubernetesオブジェクトに自動的に同期。変更時には依存するDeploymentの自動リロードも可能。ただし、Hugging Faceは高トラフィック（1分あたり1000万リクエスト以上）のため、精密な制御を優先し、手動での再デプロイを選択。
*   **ローカル開発**: Infisical CLIが開発環境に直接秘密情報を注入し、`.env`ファイルの使用を不要にすることで、セキュリティを向上させ、オンボーディングの摩擦を軽減。
*   **セキュリティとアクセス管理**: Oktaとの統合により、きめ細やかなRBACシステムを確立。Oktaグループから権限が自動的にマッピングされ、開発者、フロントエンド、バックエンドチームに適切なアクセス権が付与。監査と秘密情報ローテーションの管理も簡素化。
*   **CI/CDとインフラ統合**: GitHub Actions、OIDC認証、Terraformを介してInfisicalをCI/CDパイプラインに組み込み、セルフホストランナー内で運用することで、開発からクラウドデプロイまで一貫した生産レベルのセキュリティ基準を確保。
*   **技術的成果**: エンジニアは手動で環境秘密情報を設定する時間を削減。自動監査とRBACによりインシデント対応が迅速化し、「シフトレフト」セキュリティアプローチを推進。クラウドプロバイダー、Kubernetesクラスター、CI/CDパイプライン全体で秘密情報管理の一貫性が確保され、インフラのセキュリティと信頼性が向上。

## 詳細レポート

### What happened
Hugging Faceは、AIインフラの急速な拡大と400万人以上のビルダーによるプラットフォーム利用に伴い、機密性の高い設定データ（シークレット）の管理方法を見直す必要に迫られました。HashiCorp Vaultなどのツールを評価した後、開発者フレンドリーなワークフロー、マルチクラウド抽象化、堅牢なセキュリティ機能を持つInfisicalを選択し、既存のシステムへの移行と統合を実施しました。

### 背景
Hugging Faceのインフラは、当初のAWS単一環境から、AzureやGCPを含むマルチクラウド環境へと進化しました。この変化とプラットフォームの急成長は、以下の主要なシークレット管理の課題を引き起こしました。
*   **シークレットの散乱**: 環境間でのシークレット管理の一貫性がなく、セキュリティリスクが増大。
*   **複雑な権限管理**: チーム規模の拡大に伴い、組織のSSO（Okta）と統合された厳格なロールベースアクセス制御（RBAC）の必要性が高まる。
*   **ローカル開発の課題**: 従来の`.env`ファイルの使用は、セキュリティを損ない、開発者の生産性を低下させる。
*   **手動ローテーションの負担**: 過去のセキュリティインシデント（資格情報の露出）を受け、手動でのシークレットローテーションの負担が顕著に。
さらに、Infrastructure-as-Codeの原則に準拠し、プロジェクトごとのシークレット管理をサポートし、デプロイ時の自動化と手動制御のバランスが取れたソリューションが求められていました。

### 影響
Infisicalの導入は、Hugging Faceのシークレット管理プロセスに多岐にわたる改善をもたらしました。
*   **Kubernetes統合**: Infisical Kubernetes OperatorがInfisicalプラットフォーム内のシークレット変更を継続的に監視し、対応するKubernetesオブジェクトに自動的に同期。シークレットが変更された際には、関連するDeploymentを自動的にリロードし、コンテナが常に最新のシークレットで実行されるように保証。ただし、Hugging Faceは1分あたり1000万リクエストを超える高トラフィック環境での精密な制御のため、Operatorによる自動コンテナ再起動ではなく、手動での再デプロイを好む判断を下しました。
*   **ローカル開発**: Infisical CLIが開発環境に直接シークレットを注入することで、安全でないローカルの`.env`ファイルが不要になり、ローカル設定と本番環境の標準が一致し、オンボーディングの摩擦が軽減されました。
*   **セキュリティとアクセス管理**: InfisicalとOktaの統合により、きめ細やかなRBACシステムを確立。Oktaグループから権限が自動的にマッピングされ、開発者はプロジェクトに対する管理権限を維持しつつ、フロントエンドおよびバックエンドチームは適切に制限された読み取りまたは書き込みアクセス権を受け取る。集中化されたInfisicalプラットフォームは、監査とシークレットローテーションの管理も簡素化。
*   **CI/CDとインフラ統合**: GitHub Actions、OIDC認証、Terraformを介してInfisicalをデプロイパイプラインにシームレスに組み込み。セルフホストランナーをセキュアな環境で運用することで、すべてのデプロイが本番レベルのセキュリティ基準に準拠。
*   **技術的成果**: エンジニアは環境シークレットの手動設定に費やす貴重な時間を削減。セルフサービスワークフローによりオンボーディングと日々の開発サイクルが加速。自動監査ときめ細やかなアクセス制御により、インシデント対応が迅速化し、セキュリティの「シフトレフト」アプローチを促進。クラウドプロバイダー、Kubernetesクラスター、CI/CDパイプライン全体で一貫したシークレット管理が実現し、インフラのセキュリティと信頼性が強化。
